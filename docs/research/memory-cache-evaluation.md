# 运存缓存可行性评估：中间产物磁盘缓存 → 内存缓存

> 研究存档（2026-08）。结论先行：**可行，但不建议「纯运存」直接全局替换**——
> 它与项目「内存峰值 ≈ 单帧」的核心设计目标冲突；推荐先做**帧级内存读缓存
> （LRU，方案 A，约 0.5–1 天）**，必要时再做「内存上限 + 自动降级」的混合
> 模式（方案 B′，约 2–3 天）。本页仅评估，未实施。

---

## 1. 现状：磁盘缓存如何工作

中间产物（图片序列）当前的传递方式**完全是文件路径**：

1. 每个节点有独立工作区：`backend.for_node(node_id)` →
   `cache/nodes/<node_id>/`（工作区根为软件根目录 `cache/`，见[关键决策 #30](../decisions/21-30.md#d30)）；
2. 每次执行调用 `_job_dir(prefix)` 生成**随机 job 目录**，帧以
   `frame_%06d.png` 写入（`PNG_CACHE_COMPRESS_LEVEL = 1`，见
   [关键决策 #44](../decisions/41-50.md#d44)）；
3. `SequenceArtifact`（`domain.py`）只携带 `frames: tuple[str, ...]`（路径）、
   `width/height/has_alpha/cache_dir`——**节点间传递的是「路径清单」，不是像素**；
4. 下游节点执行时逐帧 `Image.open(路径)` 读回 → 处理 → 再写新 PNG；
5. 生命周期：启动/「清缓存」清空工作区；节点重跑成功后删除旧 job 目录
   （`snapshot_workspace` + `clear_previous_run`，见
   [关键决策 #16](../decisions/11-20.md#d16)）；失败保留上次成功产物。

设计意图：**流式逐帧**——解码/变换/编码都是「单帧在内存、写盘即弃」，
内存峰值 ≈ 并发 worker × 单帧（1080p RGBA ≈ 8.3 MB/帧，30 帧约 250 MB 原始
像素；当前并行导出内存上界 ≈ 2×workers 帧 ≈ 66 MB，见
[关键决策 #43](../decisions/41-50.md#d43)）。

## 2. 动机：改运存的预期收益

| 收益 | 说明 | 实际量级 |
|---|---|---|
| 省中间 PNG 写+读 | 链式 N 个序列节点 = 每级「读 N 帧 + 写 N 帧」；运存传递可跳过中间两级 I/O | 1080p 30 帧：一次全量写 ≈ 9.3 MB @level=1；I/O 在总耗时中占比随 SSD/CPU 不同波动 |
| 省 CPU | PNG 编码是 CPU 密集（PIL 并行 30 帧 1080p ≈ 0.4 s）；省掉中间编码 | 每次中间传递 ≈ 0.4–1.6 s（wand 路径更高） |
| 自动模式更跟手 | 参数微调重算时，若上游未变（脏传播已跳过），读缓存命中率是关键 | 见方案 A |

**注意**：脏传播机制（[执行链路](../execution-pipeline.md)第 4 条）保证
「上游未变的节点不重跑」，所以运存缓存的收益集中在**首次全链运行**与
**同一运行内多级传递**，而不是反复微调场景。

## 3. 关键风险（为什么不能直接全局替换）

1. **内存模型与现设计背道而驰**。当前刻意「内存峰值 ≈ 单帧」（[关键决策 #10](../decisions/01-10.md#d10)、[#43](../decisions/41-50.md#d43)）。
   整条序列驻留内存：1080p 30 帧 ≈ 250 MB/序列；10 节点链 ≈ 2.5 GB；
   长 GIF（如 500 帧）/高分辨率/长视频会直接 OOM。**纯运存 = 把内存峰值从
   「单帧」变回「全部帧 × 全部中间层」**，正是早期版本被流式化修掉的痛点。

2. **数据模型入侵面广**。`SequenceArtifact.frames` 是 `tuple[str, ...]`，消费方：
   - `media/backend_*.py` 约 15 个变换方法（`adjust_color`/`rewind`/`concat`/`split`/
     `merge`/`sample`/`trim`/`binarize`/`grayscale`/`contrast`/`invert`/
     `export_pngs`/`color_reduce`/`analysis_*`）逐帧 `Image.open(路径)`；
   - `nodes/process_nodes.py`：`ColorBalanceNode` 手写逐帧处理、`nodes/analysis_nodes.py`：`ResolutionViewNode` 读首帧；
   - `ui/main_window_preview.py`：`_feed_sequence_frames`（帧滑条喂路径）、`preview_path_for_node`
     （返回 `Path(frames[0])`）；
   - `nodes/parameter_panel.py`：`ParameterPanel.set_sequence_frames(list[str])`；
   - 测试：大量断言直接 `Image.open(result.frames[k])` 读路径。
   需要统一的「帧提供者」抽象（路径 | PIL Image | bytes）才能平滑替换。

3. **预览/导出/播放依赖文件**。QPixmap 可从内存 `loadFromData`，但：
   - GIF 播放走 `QMovie`（需文件路径）；
   - 帧滑条/1:1 查看/裁剪 overlay 均基于路径；
   - 导出节点（`gif_export`/`png_export`）语义是「把缓存文件复制到用户选择
     的目标」（`EXPORT_KIND`/`CACHE_FILENAME` 契约，见[关键决策 #51](../decisions/51-60.md#d51)）——**最终导出仍需要文件**。

4. **wand/ImageMagick 消费路径**。`color_reduce_sequence` 与 `_assemble_gif`
   都是 `WandImage(filename=...)` 逐帧装帧。GIF 理论上可 `blob=` 从内存加载，
   但多帧 GIF 的 blob 需要整段字节在内存（与流式冲突）；wand 逐帧 blob 改造
   面大且风险高（该路径历史上出过原生内存崩溃，见[关键决策 #12](../decisions/11-20.md#d12)）。

5. **失败/取消/清理语义**。「失败保留上次成功产物、预览仍可显示」依赖磁盘
   文件在（[执行链路](../execution-pipeline.md)第 5–6 条）；内存态进程内生存、
   清缓存/重启即失，需重新定义「上次成功产物」的落点。

## 4. 分档方案与工作量

### 方案 A（推荐，最小改动）：帧级内存读缓存（LRU），磁盘布局不变

- 做法：`MediaBackend` 增加进程内 LRU 缓存 `{job 目录/帧路径 → 解码后数据}`，
  所有读帧入口统一走 `self._open_frame(path)`（命中内存直接返回，未命中
  `Image.open` 后入缓存）；重跑/清缓存时同步失效该节点工作区的内存条目。
  `SequenceArtifact`、UI、导出、wand 路径**全部不动**（写盘仍保留）。
- 收益：省「读」不省「写」；自动模式微调重算、链式节点读上游帧时命中率高；
  实现风险极低（纯增量）。
- 工作量：**约 0.5–1 天**（读帧入口改造 ~15 处 + LRU + 失效钩子 + 少量测试）。
- 局限：中间写盘依旧（CPU 不省），内存收益有限——但它先验证「读缓存命中率
  与 I/O 占比」，用数据决定是否值得做方案 B。

### 方案 B（真正运存缓存）：序列产物整体内存化

- 做法：`SequenceArtifact` 增加内存帧变体（`frames` 支持路径或内存数据），
  backend 各方法经统一访问器取帧；UI 预览（QPixmap `loadFromData`）、
  wand 路径（逐帧 blob）适配；导出节点从内存写目标文件。
- 收益：单次全链运行省掉中间全部写+读，提速最明显。
- 代价：**内存峰值爆炸**（见 §3.1）；改造面 = domain + backend 全部变换 +
  nodes 2 处 + ui 预览 + 测试大批量改路径断言；wand blob 改造有原生崩溃史风险。
- 工作量：**约 3–5 天 + 测试/文档**。

### 方案 B′（推荐的前进方向）：混合模式——内存优先、超限自动降级

- 做法：在方案 B 基础上给内存态设**上限**（如 `帧数 × 宽 × 高 × 4 ≤ 512 MB`
  才整体驻留，超过则退回磁盘态）；磁盘写保留为「持久层」，
  内存态仅作「最近一次成功输出的热副本」。
- 收益：小序列全内存（快），大序列自动回退（不 OOM），导出/预览仍可回退文件。
- 工作量：**约 2–3 天**（在 B 的抽象之上加策略层，比 B 少改测试回退分支）。

### 不推荐

- 纯内存 + 完全去掉磁盘（导出、失败保留、预览恢复全部失去落点）。
- 仅「输出端缓存」内存化（收益极窄，仍要过一遍磁盘读）。

## 5. 建议落地顺序

1. **先测**：对典型链路（视频/GIF 输入 → 格式化 → 亮度 → 对比度 → GIF 合成）
   做 profiling，量化「PNG 写 + 读」占总耗时比例；若 < 20%，运存改造收益有限，
   应优先做其它优化（如进一步并行、减少中间节点）。
2. 实测确认读 I/O 是瓶颈 → 做**方案 A**（0.5–1 天），先吃「读缓存」收益。
3. 用户明确要求「中间产物不进磁盘」→ 在 A 的访问器抽象上做**方案 B′**（2–3 天），
   保留磁盘持久层与自动降级。
4. 只有确认目标机器内存充裕（≥ 16 GB）且序列规模受控时，才考虑方案 B 全内存。

## 6. 工作量汇总

| 方案 | 改动范围 | 收益 | 风险 | 工作量 |
|---|---|---|---|---|
| A：帧级 LRU 读缓存 | backend 读帧入口 + LRU + 失效 | 省读；自动模式受益 | 低 | 0.5–1 天 |
| B′：混合模式（内存优先+降级） | domain + backend + ui + 策略层 | 小序列全内存快；大序列安全 | 中 | 2–3 天 |
| B：纯运存 | 全链路（含 wand/导出/测试） | 最快 | 高（OOM/wand/语义） | 3–5 天+ |
